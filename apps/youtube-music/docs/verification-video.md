# 検証: PV (ミュージックビデオ) をアプリ内で再生できるか

対象は [Issue #16](https://github.com/hayato0259/pspgo/issues/16)。
検証に使ったコードは [psp-client/poc3-video/](../psp-client/poc3-video/)、
変換ツールは [tools/make_psmf.py](../tools/make_psmf.py)。

検証日: 2026-07-28 / 環境: PPSSPP 1.20.4 (macOS arm64) / pspdev v20260701

## 結論

- **映像のデコードと表示はできた。** 20 秒 (601 フレーム) を最後まで
  1 フレームも落とさずデコードし、画面に絵が出ることを確認した
- **音声と映像を同じアプリで同時に動かせた。** ただしこれは PPSSPP での結果で、
  **Media Engine の排他性を確かめたことにはならない**（後述）
- **実機での確認が必須。** ここが未了なので、アプリ内 PV 再生の可否はまだ確定していない

## 何を作ったか

PSP の映像デコーダ (`sceMpeg`) は生の H.264 ストリームを受け付けず、
Sony 独自コンテナ **PSMF** を要求する。中身は
「先頭 2048 バイトの PSMF ヘッダ + MPEG プログラムストリーム」で、
後半は ffmpeg がそのまま作れる。そこで変換ツールは 3 つのことだけをする。

1. ffmpeg で H.264 Baseline / 1 パック 2048 バイトの MPEG プログラムストリームを作る
2. 映像のストリーム ID を PSP が期待する `0xE0` に直す (ffmpeg は `0xE2` を割り当てる)
3. PSMF ヘッダを組み立てて先頭に付ける

**音声は PSMF に入れない。** PSMF の音声は Atrac3+ 固定で、
ffmpeg に Atrac3+ エンコーダが無いため。音声は別ファイルの MP3 として出し、
PSP 側では既存の `sceMp3` 経路でそのまま再生する。
結果として「Atrac3+ を用意できない」という最大の障害を迂回できた。

### 組み立てた PSMF ヘッダ

| 位置 | 内容 |
|---|---|
| 0x00 | `PSMF` |
| 0x04 | バージョン `0015` |
| 0x08 | 本体の開始位置 (大端 32bit)。**2048 の倍数でないと弾かれる** |
| 0x0C | 本体の長さ (大端 32bit) |
| 0x54 | 最初の表示時刻 (大端 6 バイト、90kHz 単位) |
| 0x5A | 最後の表示時刻 (大端 6 バイト、90kHz 単位) |
| 0x80 | ストリーム数 (大端 16bit)。映像 1 本なので 1 |
| 0x82 | ストリーム表。1 エントリ 16 バイト |

ストリーム表の 1 エントリは、先頭がストリーム ID (`0xE0`)、+4 が頭出し表の位置、
+8 が頭出し表の要素数、+12 と +13 が幅と高さ (**16 画素単位**。480x272 なら 30 と 17)。
頭出し表は作っていない (シークしないため 0 で通る)。

## 実行結果

| モード | デコード枚数 | 所要時間 | 平均 | 音声 | 備考 |
|---|---|---|---|---|---|
| 映像のみ | 601 | 4713 ms | 127.5 fps | - | 全フレーム成功 |
| 映像 + 音声 | 601 | 4720 ms | 127.3 fps | 異常なし | 同時動作で速度低下なし |

- `sceMpegGetAvcAu` と `sceMpegAvcDecode` は全フレームで 0 を返した
- 最後に出る `0x80618001` は「ストリームを読み切った」の意味で、異常ではない
- 音声を足しても所要時間は 7 ms しか変わらず、PPSSPP では互いに干渉していない

呼んだ順序と戻り値:


## 詰まった箇所

### `sceMpegAvcDecode` の描画先はポインタのポインタ

一番時間を取られた。**デコードは 0 (成功) を返すのに画面は真っ黒**という状態になる。

第 4 引数は「描画先そのもの」ではなく「**描画先のアドレスを入れた変数**」への
ポインタだった。ヘッダのコメント (`pBuffer - buffer that will contain the decoded frame`)
からは読み取れない。

```c
static void *g_display_buf;      /* ここにフレームバッファのアドレスを入れておく */
g_display_buf = topaddr;
sceMpegAvcDecode(&g_mpeg, &g_au, 512, &g_display_buf, &init_flag);
/*                                    ^^^^^^^^^^^^^^ 変数のアドレスを渡す */
```

間違えていると PPSSPP のログに
`Ignoring invalid video decode address 00000000/200` が出る。
戻り値は 0 のままなので、**ログを見ないと気付けない**。

### 最初の表示時刻は 90000 に揃える

PSMF は最初の表示時刻が 90000 (90kHz で 1 秒) である前提で作られている。
ffmpeg の既定は 0.5 秒 (= 45000) で、そのままだと PPSSPP が
`Unexpected mpeg first timestamp` を出す。ffmpeg 側に `-preload 1000000` を渡して合わせた
(`-output_ts_offset` では変わらない)。

### `sceVideocodec` は使えない

生の H.264 をそのまま渡せる低レベル API だが、**PPSSPP は実装していない**
(モジュール名は登録されているが関数が無い)。
[PPSSPP の開発ドキュメント](https://www.ppsspp.org/docs/development/ppsspp-internals/mpeg/)
にも詳細不明と書かれている。エミュレータで検証できない経路は開発ループが成立しないため、
`sceMpeg` + PSMF を選んだ。

## この検証で分かっていないこと

**Media Engine を映像と音声で同時に使えるかは、まだ答えが出ていない。**

PPSSPP は実際の Media Engine を再現せず、ホストの CPU (ffmpeg) でデコードしている。
そのため同時に動いたからといって実機で動く保証にはならない。
逆に実機で駄目でも PPSSPP では成功してしまう。

フレームレートについても同じで、127 fps はホストの CPU の速さでしかない。
実機の Media Engine で 480x272 の H.264 が何 fps 出るかは別の話になる。

判断できるのは実機だけなので、**USB ケーブル到着後の実機テストで次の 2 点を測る**。

- 映像のみ / 音声のみ / 映像 + 音声 の 3 モードで、どれが成功しどれが失敗するか
- 映像 + 音声のときの実測フレームレート (30 fps を割らないか)

PoC アプリはこの 3 モードをボタンで選べるように作ってあるので、
実機ではビルドし直さずに切り替えられる。

## 実機で駄目だった場合の代案

Media Engine を同時に使えないと分かった場合、案は 2 つある。

- **音声を Atrac3+ にして PSMF に一本化する。** ffmpeg では作れないため、
  サーバー側に Atrac3+ エンコーダを用意する必要がある (難易度が高い)
- **映像と音声を切り替え式にする。** PV を見ている間は音声を `sceMpeg` 側に任せず、
  無音の映像として扱う。実用性は落ちる

どちらも大きな作りになるため、実機の結果を見てから判断する。

## サーバー側の配信 (2026-07-29 追加)

`GET /video?yt=<videoId>&sec=<秒>` で PSMF を配信できるようにした。
yt-dlp と ffmpeg をつないで MPEG プログラムストリームを作り、
ヘッダを先頭に付けて流すだけで、ファイルには落とさない。

実際の YouTube のミュージックビデオで、
**PSP 側がデコードして画面に絵を出すところまで確認済み**。

詰まった箇所:

- **映像だけの形式は使えない。** `bestvideo[...]` を指定すると
  yt-dlp が **403 Forbidden** で失敗する (分割配信のため、
  標準出力へ流し込む取り方だと弾かれる)。
  音声と一緒になった 360p の形式 (itag 18) を選ぶと通る。
  音声はここでは捨てる (音声は従来どおり `/stream` から MP3 で配る)
- 配信しながらなので本体の長さが分からない。ヘッダに書く長さは
  再生時間とビットレートからの見積もりでよい
  (PSP 側はデータが尽きた時点で終わるため、多少ずれても再生に影響しない)
- ffmpeg の `-streamid` では映像のストリーム ID を変えられなかった。
  0xE2 のまま出てくるので、流しながら 0xE0 に書き換えている

## アプリへの組み込み (2026-07-29 追加)

再生画面で動画版を選んでいるあいだ、映像を全画面で流すようにした。

- 映像は `/video`、音声は従来どおり `/stream` から、**2 本の接続で受け取る**
- 受信は専用スレッド、デコードは描画スレッド。
  デコード結果は「今から描くバッファ」に直接書かれるので描画スレッドで行う必要があり、
  一方その場で通信を待つと画面が止まるため分けた
- Media Engine が書いた絵を消さないよう、映像があるフレームは画面クリアをしない
  (`gfx_frame_begin_keep`)。書き込み先は推測せず、表裏の切り替えを gfx.c 側で数える

### 音と映像を合わせる

デコードは音より速く回せてしまうので、放っておくと映像だけ先に進んで終わる
(PPSSPP では 127fps 出るため、3 分半の映像が 7 秒で終わる)。

**音の再生位置を基準にする。** 直前に描いたフレームの表示時刻が音より先なら、
その差だけ待つ。遅れているときは待たずに進めば自然に追いつく。

- 表示時刻は各フレームの PTS から取る。PSMF は 90000 (90kHz で 1 秒) から
  始まる決まりなので、そのぶんを引いて曲の先頭からの経過に直す
- 音の再生位置は秒では粗すぎるため `player_elapsed_ms()` を足した
  (MP3 は 1 フレーム 1152 サンプル = 約 26ms)
- 待っているあいだは入力を拾えないので上限を 120ms にしてある

### 一時停止

**一時停止中は映像を止めて、通常の再生画面 (アートワーク) に戻す。**
描かないフレームがあると、表と裏で違う絵が交互に出てちらつくため。
再開すると映像に戻る。
